# W3 · 补充、观察和处理

P-32 的实施契约，依据[衣橱整理计划](plans/wardrobe-organization.md) §5。已实现、验证并部署；证据与限制见 [W3 开发记录](history/2026-10-29-w3-organization.md)。

## 补充计划

用户显式创建，支持手工或缺口来源、名称、数量、人民币总预算（可空）、理由、备注。一个计划可关联多个季节需求；共享计划的数量不可跨行相加。编辑不会改变库存或自动调用模型。计划中/已购待入库均仅为计划；正式单品关联数量达到目标后才已完成。取消剩余独立确认：未关联则暂不需要，部分关联则完成并保留取消数。编辑已关闭计划意味着重新设置未完成部分，保留全部已关联单品。

关联走现有正式衣服选择；新衣服先通过照片/Excel 审核入库。不同 garment_id 核销数量，一个 ID 全局只能核销一个补充计划。重复操作返回原回执，其他键重复关联明确冲突。已关联衣服后来退出/删除不撤销完成事实。计划不能改成小于已关联数量。来源软删除/停用后仍展示已停用，保存原始来源快照；不删除计划和关联。

接口：GET /supply-plans（UUID 游标、20/最多100）；GET、POST /supply-plans/{id}；POST /{id}/link、/{id}/cancel-remaining。创建由客户端生成稳定 UUID，expected_version=0；其他写入版本化且幂等。图片和正式库存仍只由已有衣橱/导入服务维护。

## 决定与处理

建议仅根据明确目标和已确认资料。按单品和稳定原因保存观察、待处理、保留及撤销决定；同原因保留抑制重复建议，新原因仍可见，不自动覆盖决定。无穿着记录不会生成闲置/丢弃建议。退出前读取全部季节影响，确认重查依据；维修与退出复用 W1 生命周期事务，保持历史快照。

## 数据与兼容

追加 0009_organization：supply_plans、supply_sources、supply_links、organization_decisions。来源、核销单品均用外键，来源与关联时名称另存快照。备份精确表集合纳入四表，app_version=0.4.0-w3；旧包仍按严格版本规则拒绝直接覆盖，部署前保留 W2 完整备份。

## 决定和处理接口

- GET /organization：四季明确缺口与尚未核销的计划数量；观察/处理条目按单品 ID、原因键稳定排序分页，limit=20/最多100，cursor 不代表冻结统计快照。state=active/observe/pending/keep/repair/done/all。active 隐藏同原因已保留、已处理和归档单品；历史可通过其他分组读取。
- GET /organization/{garment_id}：该单品的全部原因和决定（最多四季400行，加有限状况原因及手工项）。
- POST /organization/{garment_id}/decision：单品版本、此原因决定版本、原因键、状态、说明。首次决定版本0；观察不改变可穿/持有状态；待处理和保留需原因，复用 W1 事件。撤销保留或待处理后，单品档案回到其他原因中最近明确保存的保留/待处理及其说明；没有剩余决定时回到未决定并清空决定原因。撤销某一原因不影响其他原因的独立记录。
- GET /organization/{garment_id}/exit-impact：返回全部启用需求的 K/U 前后数量、目标、结论、失效规则提醒和依据 token。未知资料仍按 U 计算；不把无影响或规则失效解释为衣服无用。
- POST /organization/{garment_id}/process：显式维修/改衣或转赠/出售/回收/丢弃/其他退出，携带单品版本、实际日期、原因；退出必须带当前 impact_token。复用 W1 同事务状态、版本、生命周期事件和幂等回执。
- W1 原 lifecycle retire 接口也要求 impact_token；前端生命周期退出已统一使用处理接口。旧客户端未预览时收到 IMPACT_CHANGED，不静默退出；旧幂等回执仍先返回。

原因键：excess:需求ID（重命名或改目标不自动取消保留）；condition:needs_repair/damaged；fit:unfit；overlap:稳定需求集合摘要；manual。用途重叠只在至少两件衣服都已确认覆盖同一组至少两项需求时提示，明确可能是合理轮换，不按颜色/子类判断重复。没有穿着记录不产生任何闲置结论。

每个单品/原因保存独立版本和说明。W1“继续保留”同步当前已知原因，W1 撤销/改为待处理取消原抑制；W1 显式改为未决定时同时撤销既有待处理决定，防止清单与档案矛盾；新问题不会后台改写保留。W1 开始维修、实际退出同步已有待办；完成维修或撤销退出后，相关维修中/已处理条目回到观察复核。档案、采购核销和历史图片继续保留。再次手工编辑决定是明确重新评估。

统计使用 REPEATABLE READ；退出确认在短事务内锁定单品/配置/词表相关表，覆盖并发新单品和其他季节目标写入，重算 token 后才执行。锁期间没有外部或模型调用；无异步批处理。计划数量不参与有效库存，也不属于退出影响依据。普通计划写入使用行锁、稳定创建 ID 与幂等键；同一 garment_id 跨计划核销由单品行锁和唯一约束共同保护。

## 前端路径

我的衣橱 → 补充与处理，或盘点末尾进入。补充计划支持缺口草稿和手工新增、跨季来源、编辑、关联正式单品、独立取消剩余；录入入口和审核页保留返回计划链接，正式入库后用户明确关联，不自动新增或自动核销。单品详情可主动标记观察/处理；查看单品后可回原整理清单。处理表单先读影响，再勾选确认并显式提交。

失败保留原请求与幂等键；刷新不自动重发。版本冲突可保留输入读取最新版本；过期退出影响需重新读取并再次确认。表单离开和处理面板关闭有草稿保护。默认深绿暖白、移动端单列卡片，两页签，不增加主导航或购物链接。

界面按进行中/已结束展示补充计划，桌面计划卡片可双列；数量缺口和来源说明按需展开，计数明确分页口径。决定使用带后果说明的单选卡片，保存或返回保留原筛选；退出展示跨季影响摘要与前后数量。界面实现及验证见 [W3 界面优化](history/2026-10-29-w3-ui.md)。
