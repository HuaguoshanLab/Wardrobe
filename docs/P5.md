# P5 · 历史与数据保护

日期：2026-10-26。实现历史分页/隐藏、收藏命名/取消、实际穿着记录、完整备份导出、隔离验证和确认恢复。真实云端及真机边界沿用 [P4](P4.md)。验证证据见 [本轮记录](history/2026-10-26-p5.md)，实现选择见 [D-30](adr/D-30-p5-data-protection.md)。

## 历史、收藏与穿着

- `/collections` 提供历史/收藏切换、快照详情和分页。详情可收藏、命名、记录穿着或复用为新会话；复用不调用模型，并沿用 P4 的当前可用性提示。
- 删除历史只设置隐藏元信息，不删除版本、图片、收藏或穿着记录。所有引用该版本的会话都移除对应候选；如果选中它则清空选择和锁定，不自动改选。有活动任务时拒绝删除，等待任务结束。
- 收藏绑定固定 revision，重复收藏返回已有记录；名称独立于搭配正文，取消收藏不删除历史。
- `/calendar` 按月份查看实际穿着，支持补记、修改日期/备注、删除。同日期同 revision 去重，同日可有多套；按 Asia/Shanghai 拒绝未来日期。生成或收藏不会自动写日历。
- 新增迁移 `0005_collections`：favorites、wear_records，以及 outfit_revisions 的 hidden_from_history_at/history_version。快照响应正文不增加可变状态；历史列表用包装对象返回版本。
- 创建/修改/删除均使用幂等键。PATCH 携带 expected_version，DELETE 携带整数 If-Match；失败操作可在刷新后显式重发原负载和键，放弃后重新读取新状态。

### 接口

| 路径 | 已实现语义 |
|---|---|
| GET /outfit-revisions | 历史可见记录，items 为 revision/version/hidden_from_history_at 包装；游标分页 |
| DELETE /outfit-revisions/{id} | 隐藏历史并清除相关会话选择，返回说明；不删除底层快照 |
| GET/POST /favorites | 分页；创建体 revision_id/name，重复版本返回已有收藏 |
| PATCH/DELETE /favorites/{id} | 修改名称或取消收藏 |
| GET/POST /wear-records | start/end 日期过滤及游标分页；创建体 revision_id/worn_on/notes，缺省日期为今天 |
| PATCH/DELETE /wear-records/{id} | 修改日期和备注或删除；日期冲突返回 WEAR_EXISTS |

以上路径相对 `/api/v1`。默认 limit=20、最大 100；列表按 created_at/id 倒序，日历页面将已加载记录按穿着日期展示。精确字段见 OpenAPI。

## 备份与恢复

设置页点击“创建完整备份”，完成后下载 ZIP；下载有效期为七天。备份包含 public 的完整应用表和 checkpoints 的四张适配器表，以及 media_assets、导入原件和 outfit_images 引用的文件。已软删除衣服和已隐藏历史仍完整保留。环境变量、API 凭据、模型缓存及先前备份不在包内。

备份格式 v1：`manifest.json`、`database.json`、`media/<服务端存储键>`。数据库文件只包含行数据，使用 PostgreSQL row_to_json / json_populate_recordset 往返；不包含或执行上传者提供的 SQL、DDL 或脚本。清单包含应用版本、Alembic revision、检查点适配器包版本、创建时间、各文件大小与 SHA-256。仅接受精确匹配版本；P6 识别迁移后的兼容版本和旧包边界见 [P6 识别](P6-recognition.md)。哈希校验不等于可信来源认证。

默认上限：总包/解压内容 2 GiB、10,000 个数据文件（含 database.json，因此最多 9,999 个媒体文件；manifest.json 另计）、数据库 JSON 128 MiB、清单 4 MiB。超限明确失败，不裁剪数据。Nginx 允许恢复上传最大 2049 MiB 请求体，后端检查文件及请求上限；普通导入仍保持 210 MiB 请求体上限。不会自动清理备份、恢复点或临时验证材料，需预留磁盘空间；P6 已验证合成图片负载接近 2 GiB 的完整往返，性能、故障与剩余边界见[容量验收](history/2026-10-27-backup-capacity.md)，不能替代真实用户规模证据。

### 维护屏障

- 新增独立 `controller` 服务，使用与 API/worker 相同代码镜像，挂载独立 `wardrobe_control_data` 卷。控制记录、事件、幂等键、确认令牌和恢复阶段采用 fsync＋原子重命名，独立于目标业务库。
- 共享文件锁覆盖普通 API 请求（含 GET 天气/偏好可能产生的写入）和 worker 的 sweep/claim/run 全过程，直到 Checkpointer 连接关闭。维护先写持久标记，再等待独占锁，最多 330 秒；不能静止则失败并退出维护。
- 健康、能力、只读 Job/SSE、备份恢复控制接口不持有整个请求生命周期锁。业务访问在维护期间返回 503 MAINTENANCE_MODE；前端显示维护提示。控制器不会因普通 worker 暂停而死锁。
- 进程退出自动释放操作系统锁，但持久维护标记保留；控制器重启先恢复审计，再放行业务。单一控制器锁防止多实例并行切换。
- 屏障适用于本应用的 API/worker/controller 路径；维护期间不得通过外部 SQL、手工迁移或其他进程修改业务数据/媒体。

### 恢复顺序与回退

1. 上传返回 restore_id，控制器校验包路径、大小、重复条目、链接、版本、清单、图片引用和摘要；在临时 `wardrobe_restore_<UUID>` PostgreSQL 数据库执行本地可信迁移及 Checkpointer 初始化，再按约束试导入行数据。验证库随后删除。
2. 验证通过返回数据摘要及 30 分钟确认令牌，绑定包哈希与目标 data_epoch。用户勾选确认后 apply；重复同键同内容返回同一控制任务，其他覆盖请求拒绝。
3. 维护独占后重查令牌/世代/包哈希并重新隔离验证，导出当前数据库和引用媒体到该 restore_id 目录的 recovery.zip 恢复点。
4. 先将缺少的不可变媒体流式写入并 fsync。同名不同内容拒绝覆盖；原媒体始终保留。写文件阶段失败只可能留下无引用新文件，不会损坏原数据。
5. 在一个 PostgreSQL 事务内替换 public/checkpoints 行数据、终止旧活动任务及租约、写入新 data_epoch。SQL/进程失败由 PostgreSQL 回滚，原库和原媒体仍成对有效；不需要执行第二次破坏性回滚覆盖。
6. 提交后读取新世代确认成功。若进程恰在提交后退出，重启通过持久 new_epoch 与数据库世代对照认定已提交；不重新覆盖、不重新发模型调用。尚未提交则标 interrupted，保留原数据；不自动重跑旧恢复。

恢复不物理删除当前媒体中的额外文件；业务引用恢复到备份时点，未引用文件保守保留。成功后客户端按 data_epoch 清除旧缓存、草稿、幂等操作与事件游标；独立恢复控制 ID 保留以便查询结果。备份中的 queued/running/cancel_requested 均转 interrupted，继续搭配需要用户显式操作。

控制目录里的 recovery.zip 是完整同格式恢复点，可由管理员复制出来再通过验证/确认入口恢复；尚无恢复点列表或一键回退页面。磁盘损坏和操作系统崩溃级别的恢复仍依赖宿主持久化可靠性，当前故障证据覆盖进程退出和文件/数据校验失败。

### 控制接口

- POST /backups：Idempotency-Key，202 返回 JobAccepted；GET /jobs/{id} 和 SSE 返回 backup_export 结果；GET /backups/{id}/download 下载。
- POST /restores/validate：multipart 字段 file、Idempotency-Key，202 返回 RestoreView，状态 validating。
- GET /restores/{id}：验证/恢复状态、摘要、有效确认令牌或结果。状态变化由只读轮询恢复。
- POST /restores/{id}/apply：confirmation_token、Idempotency-Key，202 返回同一 restore_id 对应控制 Job。Job 查询和 SSE 使用与普通任务一致的事件结构；数据来自控制目录。
- 维护任务不支持通用 cancel/retry，返回明确错误。失败导出重新创建；失败或过期恢复重新上传验证。不会伪装成普通队列任务或把恢复进度放入将被覆盖的表。

## 运行

根 README 的 `docker compose up -d --build --wait` 同时启动 controller。纯本机运行需 API、worker、controller 使用相同数据库、媒体根和控制根；另开终端执行 `uv run python -m app.backup.worker`。配置 `WARDROBE_CONTROL_ROOT`（Docker 为 /data/control）。验证库创建需要数据库账户拥有 CREATEDB 权限；当前本地 Compose 账户满足要求。此应用仍按可信本机/家庭局域网使用，不提供公开互联网认证。

自动化恢复测试在独立 `wardrobe_test` 或独立 Compose 项目执行。生产入口不会在测试中 apply；普通浏览器回归只新增自有数据、创建备份和隔离验证。测试命令和隔离环境约束见本轮记录。
