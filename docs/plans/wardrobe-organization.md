# 衣橱整理 · 生命周期与四季盘点实施计划

日期：2026-10-29。状态：**W1～W4 已实现、验证并部署**。

用户要求管理单品生命周期，按春夏秋冬盘点需要、缺少、多余、新增和需要处理的衣服，并明确询问盘点表自行修改能力；本轮要求“先生成计划”。需求入口为 [PRODUCT](../PRODUCT.md) P-30～P-33，优先级变更见 [D-35](../adr/D-35-wardrobe-organization.md)。

本计划优先于原 [P7](P7-advanced.md)，按 W1 → W2 → W3 → W4 逐项完整交付，再接续 P7。每项先固定规则与契约，完成后端、前端、迁移、验证及本地部署后才进入下一项；W1～W4 已依次获用户明确实施授权，当前进度见 [W1 记录](../history/2026-10-29-w1-lifecycle.md)、[W2 记录](../history/2026-10-29-w2-inventory.md)、[W3 记录](../history/2026-10-29-w3-organization.md) 和 [W4 记录](../history/2026-10-29-w4-seasonal.md)。下文状态拆分、字段、页面位置与算法均为工程默认，实施时可据证据调整并记录，不冒充用户逐字段确认。

## 1. 目标与当前缺口

最终能回答：每件衣服处于什么阶段；本季各类衣服是否够用；哪些值得补充、观察或处理；换季整理完成了哪些动作。

已检查基线：`5945c8f`，已有 Garment 图片、品类、季节/场合/标签及 available/unavailable；已有软删除、不可变搭配快照、实际穿着记录、幂等操作设施与备份恢复。该基线当时尚无购入信息、细分品类、生命周期事件、季节目标、补充/处理清单或整理会话；当前完成状态以上方阶段记录为准。

- 新功能基于真实单品 ID，不能维护一份可任意修改的“库存总数”。
- 新增字段可未知；老单品的录入日期不能当购买日期，缺少状况记录不能默认完好。
- 使用现有品类代码作为稳定大类，增加可选子类；不改旧品类代码、不让 AI 自动回填全部旧衣服。
- 统计与建议均由后端明确规则生成，用户改数据后重新计算；本计划四项不依赖新增模型调用或新外部服务。
- 生活习惯、季节目标与长期穿搭偏好分开；不引入自动偏好学习、购物链接或“到年限自动淘汰”。

## 3. W1 · 单品生命周期

已实现并通过本轮验证，最终接口及工程细则以 [W1](../W1.md) 为准；下文保留原实施范围。

### 3.1 档案与状态

可选补充：来源（购买/获赠/其他）、获得日期、购入金额、收纳位置、子类、状况、合身情况及备注。首版金额以人民币元录入、精确小数存储，未知与 0 元区分；不扩展汇率或财务分析。获得日期未知可不填，实际获得日期不得在未来。

状态按职责分开，不做互相混淆的大枚举：

| 维度 | 计划表达 | 对业务的影响 |
|---|---|---|
| 是否拥有 | 持有 / 已退出；退出原因可为转赠、出售、回收、丢弃、其他 | 已退出不参与当前库存或新搭配，保留档案和旧快照 |
| 存放状态 | 日常存放 / 换季收纳，可填位置 | 均仍是库存；收纳不自动判定缺货或淘汰 |
| 临时可用性 | 沿用可穿/暂不可用，补可选原因（待洗、维修、其他） | 暂不可用排除新搭配，不必然减少长期保有量 |
| 衣物状况 | 未知 / 完好 / 轻微磨损 / 需要维修 / 严重损坏；合身情况另记 | 用于待核对、维修或处理提示，不由照片擅自确定 |
| 整理决定 | 未决定 / 继续保留 / 待处理，可填原因 | 决定不是实际退出；“保留”可撤销，仍计入库存 |

“收纳/取出”和“可穿/不可用”分别操作，不能取出时抹掉原来的待洗原因。单独记录需要维修不自动证明不能穿；用户把衣服标为不可用时才改变临时可用性。已退出是硬排除条件，不能通过把 availability 改为 available 绕过。

### 3.2 生命周期动作

- 明确保存购入/补录、状况变更、收纳/取出、开始/完成维修、保留决定、退出等事件；记录发生时间、保存时间、原因和版本。
- 事件更正通过关联的更正记录保留过程，不能静默抹掉已执行的退出。误操作可通过显式“撤销退出”恢复原单品 ID，重新核对可用性；真实重新购入的另一件衣服仍需新建 ID。
- 退出必须单独确认去向/日期，待处理不自动退出。退出与旧的“删除档案”分开：删除仍保留既有软删除语义，旧 deleted_at 不追溯解释为已丢弃。
- 退出后保留单品历史入口与照片；默认衣橱排除，档案筛选可查看。用户之前保存的搭配、收藏和穿着记录保持原样。
- 历史穿着继续从 WearRecord 推导，按同单品同日去重；没有记录只显示“无记录”，不编造初次穿着、实际使用年限或剩余寿命。

### 3.3 技术与完成门槛

- 增加单品管理资料、稳定子类引用和生命周期事件的持久层；具体表名和字段在 W1 契约冻结时确定，追加迁移，不改写历史迁移。
- 统一“当前可参与搭配”的后端判断，覆盖候选查询、锁定冲突、历史复用、调整和最终提交；保留旧 availability 接口语义，避免两份互相矛盾的状态。
- 保存/退出/撤销使用版本校验与幂等回执；退出与生成并发时，最终提交必须重查。已锁定衣服退出时保留历史并提示冲突，不自动解锁。
- 迁移默认保留旧可用性和所有原属性；新资料未知，不改变旧导入确认、Excel 模板或图片/品类必填约束。旧导入无需新字段也能入库；首版从单品详情补录新资料。
- 验证：旧库升级、事件更正、重复退出、误退出撤销、删除与退出区别、并发生成、照片与旧快照不变、新数据完整备份恢复。
- 完整前端状态：空资料、保存中、失败原请求重发、版本冲突、离开保护、退出确认、历史记录查看；浏览和保存档案零模型调用。

## 4. W2 · 可编辑四季盘点

已实现、验证并部署，最终契约与边界见 [W2](../W2.md)；下文保留原实施范围。

### 4.1 用户可编辑内容

- 为春/夏/秋/冬创建独立目标表，可复制已有季节为草稿，复制不覆盖目标季节已有配置。
- 需求行支持新增、改名、排序、停用/删除；指定大类、可选子类、可选场合与标签，目标数量下限/上限、备注。稳定 ID 不跟随名称变动。
- 目标为非负整数且下限不大于上限；可都留空表示未设目标，0～0 表示不计划保有该类，不与未知混用。
- 需求行名称不决定归类。修改名称不改变匹配规则；“通勤衬衫”必须有对应大类/子类/场合规则，不能仅凭标题猜测。
- 子类在稳定大类下维护，可使用初始词表并补充自定义子类。修改/停用有引用的子类时显示影响；更换单品大类时同时验证子类归属。
- 可从行内打开已匹配、待核对及不计入的单品，修改季节/子类/场合/状况后重新核算。**实际拥有、有效数量及差额只读，不提供手改总数。**
- 删除需求行不删衣服或其分类，也不清理历史整理总结；涉及未完成清单时提示转移或保留关联来源。

### 4.2 统一统计口径

每行展示目标、已匹配持有数量、确认符合需求数量、待核对数量、暂不可用数量和结论。所有集合按单品 ID 去重，从完整数据计算，不在浏览器把当前分页相加。

| 规则 | 处理方式 |
|---|---|
| 季节、子类、场合和标签 | 不同字段组之间 AND，同字段多个允许值 OR；未设限制的字段不参与判断 |
| 缺少用于匹配的属性 | 进入可能匹配的待核对集合，不能视作已确认符合或确定不符合 |
| 确认符合长期需求 | 持有、非示例、未删除，匹配该行，用户确认状况为完好/轻微磨损且合身或已确认不适用合身检查 |
| 待洗、普通临时不可用、换季收纳 | 满足其他条件时仍计入长期有效数量；另显示当前可穿数量，不因洗衣建议购买 |
| 需要维修、不合身、严重损坏 | 仍属持有库存，但不作为已确认有效数量；单独展示可维修/改衣的补足路径 |
| 已退出、已删除、导入草稿、示例 | 不计入当前真实库存；待处理但尚未退出的衣服仍按真实状况计算 |
| 跨季/跨用途 | 可覆盖多个需求行；标记重复覆盖，不把行数量或缺口简单相加为独立衣服总量 |

定义：目标下限 L、上限 H，确认符合数量 K，仍可能符合的待核对数量 U（与 K 不重叠）。

- 目标未设置：仅展示事实数量，不给缺少/超额结论。
- K < L 且 K + U >= L：显示“先核对”，不确定购买缺口。
- K + U < L：显示“按已录衣橱至少缺 L − K − U 件符合条件的衣服”；先核对未录入、可维修及跨用途替代，不直接生成订单。
- L <= K <= H：显示“已确认数量达标”，仍保留待核对提示；待核对完成可能改变结论。
- K > H：显示“超过自定目标 K − H 件”，不挑选等量衣服强制淘汰。

例：目标 3～5、K=2、U=2 时先核对；K=2、U=0 时缺 1；目标 6～8、K=10 时超出 2，但没有自动退出动作。所有“缺少”结论仅针对用户已录入并配置的衣橱，不宣称掌握现实中所有衣物。

### 4.3 如何给初始数量建议

- 手动填写始终可用；默认不预填一套声称适合所有人的四季件数。
- 可选向导收集城市/用户自定季节时段、各用途每周使用天数、洗衣间隔、晾干天数、该类单件允许重复穿次数、备用件数、个人目标上限/收纳偏好。
- 对日常轮换类给可解释的粗估下限：向上取整（每周使用天数 ×（洗衣间隔 + 晾干天数）÷ 7 ÷ 单件允许重复穿次数）＋备用件数。参数必须有效；这是容量估算草稿，不是卫生或服装寿命标准，也不声称优化了各用途之间的共享。
- 外套、正装等不适合洗衣周期估算的需求行，使用用户设定目标；城市与季节用于选择要核对的需求，不能单凭地名编出衣服件数。上限由用户明确设定。
- 示例：每周用 7 天、每 3 天洗、1 天晾干、每件穿 1 次、备用 1 件，估算下限为 5；页面显示全部参数，用户可修改或不采用。
- 向导结果只预填目标草稿，点击保存才生效；以后修改习惯不会后台覆盖已有自定目标。

### 4.4 完成门槛

- 目标 CRUD、子类/规则校验、模板复制、幂等/版本冲突、归类修改和服务器统计形成完整闭环。
- 验证未知/零目标、上下限非法、子类跨大类、跨季重叠、标签删除、同一行去重、多行覆盖、退出/撤销/待洗/收纳、维修及未知状况。
- 固定数据集精确核对上述公式和提示；修改单品后所有受影响行刷新，响应标明同一统计时点与配置版本，不能拼出相互矛盾的计数。
- 验证旧单品不会因资料未知突然禁止搭配，目标修改不改变衣服或已保存快照；在隔离 500 件、多页单品数据上验证完整统计与查询性能。

## 5. W3 · 补充、观察和处理清单

已实现、验证并部署，最终契约与边界见 [W3](../W3.md)；下文保留原实施范围。

### 5.1 建议和决定分开

- 待补充：来自明确缺口或用户手工添加，保存来源需求、理由、计划数量、可选预算/备注；只有用户接纳后成为计划。
- 待观察：来自超出自定目标、规则可证明的用途重叠或用户主动标记。相同颜色/子类只能提示功能可能重叠，不能断言是重复购买。
- 待处理：用户确认不合身、损坏或不需要后，选择保留、维修/改衣、转赠、出售、回收或丢弃；建议不会替用户执行。
- 季节性无记录只能按用户配置并实际覆盖的季节区间提示；新录入、记录不足、非对应季节不判断闲置。首版不因没有穿着记录自动提出丢弃建议。
- “继续保留”保存原因并抑制同一原因的重复处理建议，直到用户撤销或明确重新评估；仍显示真实超额数。不同新问题可提示，但不能覆盖保留决定。

### 5.2 补充与新增入库

- 计划状态：计划中 / 已购待入库 / 已完成 / 暂不需要，可编辑数量、备注和状态；不接入商城、支付或购物链接。
- 已计划数量单独显示，不能计为库存；缺口提示同时说明已有计划，避免生成重复补充项。跨季、跨用途行可关联同一补充计划，不逐行强制购买。
- 已购待入库仍需走现有照片/Excel 审核确认。支持关联已有正式单品或新入库单品；按不同 garment_id 核销计划数量，重放确认不会重复入库或重复完成。
- 批量购入允许部分完成，取消剩余数量是独立动作。正式库存始终来自单品，手工标记“已购”不增加库存。
- 需求目标调整后重新提示当前缺口，但不自动删除已有计划或把用户已买的衣服撤回；关联单品后续退出也不把历史采购记录改为从未完成。

### 5.3 处理动作

- 执行前显示该单品退出后影响的全部季节/需求行，包括“已确认有效数量将低于目标”或“需先核对”；多行共享必须统一重算。
- 预览不写状态。确认时重新检查单品、目标和统计依据的版本；有变化则刷新预览，不按旧结论退出。
- 选择维修走 W1 事件；确认转赠/出售/回收/丢弃后走 W1 退出事务，记录日期和原因。没有“一键按超额数量自动删除”。

### 5.4 完成门槛

- 测试保留决定持久性、撤销和新原因区分；新/旧目标变化、跨季共享、采购部分完成、重复关联、并发入库及退出。
- 验证采纳建议不等于购入，加入待处理不等于退出；清单修改不改变历史搭配，实际入库/退出正确刷新库存。
- 清单、决定、来源引用及生命周期事件完整备份恢复；删除/停用需求行不产生悬空引用或丢失已执行记录。

## 6. W4 · 换季整理流程

入口：我的衣橱 → 换季整理 → 选择季节与整理范围 → 核对分类/状况 → 调整目标 → 查看缺少/重复 → 逐件确认收纳/维修/退出/保留 → 保存总结。

- 整理会话保存季节、范围、进度、已核对单品和待办，可中断后继续。会话草稿与真实动作明确区分，不把点击“下一步”当批量修改许可。
- 修改资料、目标、实际收纳或退出分别显式保存；完成总结不会再重复执行。退出整理不回滚已经确认的现实动作，离开时说明已完成/未完成项。
- 批量操作先展示对象和动作，逐项版本校验及幂等结果；一件冲突不伪装全批成功，重试只处理未完成项，已完成项不重复执行。
- 其他页面修改衣服或目标后标记相关核对结果过期，继续前读取最新状态，避免对已退出衣服再次处理。
- 完成时保存不可变总结：目标与规则版本、统计时点、核对覆盖、未解决项、实际动作及当时缺口；不把未处理建议写成已完成。衣服之后变更不改旧总结。
- 已完成总结可查看；再次整理创建新会话，沿用目标配置但重新统计当前衣橱，不复制旧缺口为当前事实。

完成门槛：真实浏览器完成一轮整理；验证中断恢复、跨页修改、部分失败、重复提交、取消未保存草稿、已确认动作不回滚、总结不可变与完整备份恢复。全流程零模型调用。

| 领域 | 计划持久化内容 | 主要职责 |
|---|---|---|
| 单品管理 | 扩展资料、子类、生命周期事件、保留决定 | 保留 garment_id，集中状态与退出校验 |
| 四季盘点 | 季节配置、目标行、筛选规则及版本、可选生活习惯 | 目标可编辑；当前数量由单品派生 |
| 整理清单 | 补充计划、关联单品、观察/处理决定及理由 | 用户决定与当前计算建议分离 |
| 整理会话 | 草稿进度、逐项执行回执、完成总结及引用 | 支持恢复，保留历史事实 |

具体 schema、接口路径、索引与迁移在对应阶段实现前写入 CONTRACTS/ARCHITECTURE，并同步 OpenAPI、前端生成类型及运行时校验。本轮不预造空表、空路由或伪造新接口已可用。

- 领域规则保持纯计算；数据库聚合和事务在 service/repository；路由只做协议映射。前端按单品、盘点、清单和整理流程拆职责，复用公共 UI 和原操作恢复机制。
- 每阶段审查备份精确表集合、迁移版本、图片/快照/总结引用、恢复校验、维护屏障及 data_epoch 清理；追加迁移后同步就绪检查。
- 旧备份兼容沿用明确版本规则；升级前保留可恢复点和旧版本标识。若做旧包转换必须另写转换测试，不放宽校验假装兼容。
- 退出不释放历史图片；关联已删除/退出单品的旧总结仍能解释当时行为。保守媒体保留策略不在本计划中改为自动清理。
- 目标/状态/库存计算作为普通业务操作，不触发模型；后续若增加“AI 整理建议”，另定显式触发、预算及证据，不作为 W1～W4 完成前提。

## 8. 交付检查与下一步

每阶段交付：相关需求与契约 → 迁移和后端规则 → 前端完整入口 → 领域/真实 PostgreSQL/组件/隔离 E2E → 备份恢复与旧数据摘要 → 本地部署只读冒烟 → 独立开发记录。测试按当前阶段风险覆盖，不用一张截图代替业务验收。

关键验收矩阵：

| ID | 场景 | 必须结果 |
|---|---|---|
| W-A01 | 旧衣服没有新增资料 | 原可用状态保留，购买日期/状况未知，不禁止原搭配 |
| W-A02 | 待洗或收纳一件完好衣服 | 长期数量不减少，临时不可用才排除新搭配 |
| W-A03 | 改盘点名称、目标或归类 | 名称不偷偷改规则，目标合法，归类后服务端重新统计 |
| W-A04 | 同一衣服覆盖春秋及多个用途 | 单行去重，总库存唯一计数，显示共享覆盖 |
| W-A05 | 目标不足但存在未知单品 | 依 K/U 规则给核对或最低缺口，不能假定未知不符合 |
| W-A06 | 保留一件超额衣服 | 超额数保留，同原因处理建议被抑制，决定可撤销 |
| W-A07 | 计划购入两件，仅确认一件 | 实际库存只增加已入库件，计划部分完成，重放不重复 |
| W-A08 | 单品退出造成其他季节缺口 | 预览列明影响，确认重查，旧快照和图片不变 |
| W-A09 | 锁定衣服退出或退出与生成竞争 | 新结果不能使用退出单品，明确冲突，不自动解锁 |
| W-A10 | 整理中断/批量部分冲突 | 恢复真实进度，已确认动作不重复，未完成项可重试 |
| W-A11 | 完成后修改衣服或目标 | 新统计改变，旧总结与搭配快照不变 |
| W-A12 | 新数据备份、隔离恢复及旧客户端重连 | 数据/引用一致，旧缓存失效，不重新执行整理动作 |
