# P7.2 · 穿搭轮换契约

日期：2026-10-30。产品依据 P-24；阶段计划见 [P7](plans/P7-advanced.md)。实际验证与部署状态见 [开发记录](history/2026-10-30-p7-2.md)。

## 条件与统计

`Requirements.rotation_mode` 为 `normal | avoid_recent | less_worn`，省略时为 `normal`。旧会话、草稿和已保存响应兼容；非法值拒绝。核对条件和切换草稿均不生成任务。

- `normal`：保留原候选与顺序，不查询轮换统计。
- `avoid_recent`：以提交时 Asia/Shanghai 日期为截止，含当天共 7 个自然日。真实单品 ID 集合相同为完整重复；top/bottom/dress/outerwear ID 集合相同为主体重复。顺序和 revision ID 不影响判断，空主体不判为主体重复。
- `less_worn`：含当天共 30 个自然日；单品按实际日期去重计天数，默认比较主体单品的平均记录天数。没有主体时比较实际选择的单品；指定替换只比较新替换项。鞋包不会拉高主体衣物的轮换排序。

统计唯一来源为 WearRecord JOIN OutfitRevision，包含 AI 和手动来源，不读取列表 API，也不以生成、收藏或浏览代替穿着。数据库查询读取窗口内全量记录，流式按 500 行处理；相同组合合并。历史删除衣服的快照仍参与统计，当前候选仍由原可用性规则筛选。

没有记录时明确“轮换依据不足”，0 天只表示期间无记录，不能推导从未穿过或真实闲置。

## 冻结、排序和结果

显式生成/调整的提交事务冻结 `Job.input_snapshot.rotation`（日期、时区、7/30 天窗口、记录条数/记录天数、单品天数与组合签名）；上下文直接复用该快照。重发同幂等键、任务恢复或已收到模型响应的重放不重新读取统计。补记、改日、删除只影响下一次显式提交，显式失败重试也使用新提交的统计。

硬约束校验后才排序：本次条件/完整度未满足项数量优先，再比较重复与否或平均记录天数；相同分数稳定保留模型顺序。排序限于模型已返回的最多三套合法方案，不声称搜索整个衣橱的最优解。调整仍只返回一套，模型在可动范围内选择，后端验证并解释；不为软目标额外发起重试。

轮换不改变真实候选、锁定、全部非目标项保持、不可用和未知属性规则。只有重复合法时保留方案并解释，不制造 no_match。主体保持而只换鞋包时明确主体重复；不把固定项作为可更换目标。

`Revision.request_snapshot.rotation` 保存结果依据：mode、as_of、start、timezone、record_count、record_days、full_repeat、body_repeat、message、items（garment_id/name/wear_days，仅少穿模式显示）。旧版本无此字段或 null 时不显示轮换卡片。当前结果和历史详情使用同一组件，不用当前记录重算旧解释。

## 模型与兼容

提示版本 `outfits-v5.2-rotation`；显式提供每套必须保留和禁止出现的 ID。模型最多接收 50 个近期组合签名和当前最多 500 件候选的穿着天数，超出标记 `combinations_truncated`；完整统计留在任务中，由后端核对。仍沿用两次输出尝试/单任务四次调用总上限及 300 秒时限，没有新增轮换循环。

旧提示未发送的真实请求按既有 PROVIDER_CONFIG_CHANGED 阻止，已收到持久响应优先复用。旧已保存版本不改写；新字段采用 JSON 快照，不需要数据库迁移，仍为 0011_manual_outfits。

备份 app_version 更新为 `0.7.2-rotation`，沿用精确版本恢复。旧备份需在对应旧版本环境恢复；在线升级不清库、不重写旧版本。新模式、统计、结果依据随原 Job/revision JSON 纳入备份。

## UI

沿用搭配条件页，原生单选卡片有独立标签、键盘焦点和说明；任务期间禁用。日期/城市变动清除旧天气，保留可复用条件及轮换选择。生成页面和历史详情显示冻结依据、统计范围、无记录或重复限制。模式选择不新增底部导航，也不自动修改长期偏好。

2026-10-30 界面优化：模式按固定窗口对比，结果先显示摘要与保持项限制；原始说明、冻结日期和单品天数可展开，0 天显示“期间无记录”，空记录可进入日历查看。实际验证与部署见 [界面优化记录](history/2026-10-30-p7-2-ui.md)。
