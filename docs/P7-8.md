# P7.8 · 旅行胶囊衣橱

需求：PRODUCT P-27。当前交付状态和验证证据见 [开发记录](history/2026-11-11-p7-8.md)。

## 用户行为

入口：穿搭记录 → 旅行胶囊衣橱（`/collections/travel`）。保留原四项主导航。

- 创建一个中国大陆目的地、1～7 个连续日期的行程；逐日选择主要场合，可手填天气。行程名称 1～60 字，补充要求最多 1000 字。
- 必带单品最多 20 件，至少安排一天；期望携带数量 1～50 件为软目标。目标无法达到时显示实际数量和差额，不删减每日必要衣物来凑数，不宣称全局最优。
- 每天一套：上装＋下装或裙装，及鞋。每套 1～20 件。普通搭配的最多三套协议完全不变。
- 允许重复穿时，明确展示上装、下装、裙装跨日使用；关闭重复穿后，这三类基础衣物不跨日重复。鞋、包、外套及配饰仍可复用。清洁安排由用户判断，不自动改待洗状态。
- 保存行程、刷新、查看历史、勾行李都不调用模型。点击生成后，一个持久任务规划整个行程，不拼接普通生成会话，也不修改今日穿搭会话。
- 调整一天时，其余天的完整图片和属性快照保持；已有条件草稿与方案不同，先生成完整行程。调整完成后重新去重清单，仍存在单品保留已收拾状态，新增单品标记待收拾。
- 未完成、失败、取消、中断都保留此前可用版本；不会展示半段输出为完整方案。历史版本可分页查看，不能直接覆盖当前版本。
- 只有用户确认“这天穿过”才写实际日历，禁止未来日期。确认从固定旅行日快照创建手动确认来源的 OutfitRevision 与 WearRecord，保存 travel_day 来源标识；不同操作键重复确认同版本同日也只生成一条记录。原衣服后来变化不改旧快照。
- 删除计划为软删除，保留版本、图片与已有实际穿着；不承诺从旧备份中抹除数据。

## 天气与事实边界

手填值优先，0℃有效。选择和风城市时须匹配已有城市搜索记录；不允许伪造坐标来源。任务读取 `weather/v1/daily` 七日预报，按北京时间对应日期匹配，有效时效一小时；超出范围、缺失、服务失败时明确为 unknown。手填城市直接支持手填/未知，不使用今日实况替代未来预报。

天气和偏好冻结在任务中，重放使用原上下文；结果显示生成时快照时间，不声称出发时仍有效。未知单品属性不补全，模型仅返回日期与真实衣服 ID；界面事实说明由后端给出。参考：[和风每日预报](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)、[千问结构化输出](https://help.aliyun.com/en/model-studio/qwen-structured-output)。

## 持久化与任务

- 新增 `travel_plans`（条件、版本、当前任务/版本、打包状态、软删除）和 `travel_revisions`（不可变每日快照、提交条件、来源、警告）。行李清单由每日快照按 garment_id 精确去重；勾选状态是计划内的独立集合。
- 追加迁移 `0014_travel`，不修改原业务行；有旅行数据时禁止 downgrade 删除表。
- `services/travel` 管保存、提交、预报、执行、发布及实际穿着；`domain/travel` 校验完整日期、真实候选、必带、完整组合、不重复穿、保持日期和携带差额。
- `travel_generate` 使用现有 Job/租约/心跳/取消/事件与 ModelCall 账本。整次任务最多两次模型请求（首次＋一次无效输出纠正），从提交起五分钟总期限，单请求最多 120 秒，无传输自动重试。
- `travel-v2` 先规划共享单品池再分配日期，避免逐日挑选新鞋包。客户端不能放宽服务端上限；已发但无回执的调用中断，不盲目补发付费请求。
- 提交冻结可用候选、版本、偏好和条件；最多 500 件候选。发布前对整套结果重新锁定并检查当前可用性及版本。失效必带、提交期间衣服变化明确阻塞。
- 每个计划行锁＋expected_version；写入先查 OperationReceipt，重复原请求返回原回执。模型请求不持有数据库写事务。结果、当前版本指针、打包集合、任务终态与事件同事务提交。
- 打包可与任务同时操作，发布取最新勾选集合并与新清单求交集。条件编辑/删除在运行任务期间拒绝。

## HTTP 协议

所有写操作沿用 Idempotency-Key；字段以 `schemas/travel.py` 与生成 OpenAPI 为准。

| 方法 / 路径（`/api/v1` 下） | 语义 |
|---|---|
| GET /travel-plans?offset=0 | 每页最多 20 个计划，创建时间倒序，offset 显式翻页 |
| POST /travel-plans | 保存条件，不生成 |
| GET /travel-plans/{id} | 条件、当前版本、行李及任务 ID |
| PATCH /travel-plans/{id} | expected_version＋完整新条件，原方案保持 |
| DELETE /travel-plans/{id} | JSON expected_version；软删除，原键重放可读回执 |
| GET /travel-plans/{id}/revisions?offset=0 | 每页最多 20 个不可变历史版本，版本号倒序 |
| POST /travel-plans/{id}/generate | expected_version，可选 adjust_date/message；返回 JobAccepted |
| POST /travel-plans/{id}/packing | expected_version、garment_id、packed |
| POST /travel-plans/{id}/wear | revision_id、day、notes；只确认当天/过去实际穿着 |

任务结果独立为 `{travel_id, travel_revision_id}`；不塞入普通 OutfitResult 的三套 revision_ids。

## 前端恢复与备份

行程表单草稿存于 `wardrobe.travel.draft:{id|new}`，未填完也保留；提交前持久化原 URL/内容/操作键。网络失败提供原操作重发，刷新不自动提交。确定的 4xx 冲突清除待发操作，保留表单，可返回详情读取最新版本后重新编辑。版本冲突不静默覆盖。历史、任务及主列表由 Query 管理，data_epoch 变化清理全部旅行草稿、待发操作和查询缓存。

备份精确兼容更新为 `0.7.8-travel` / `0014_travel`。全部新表、当前版本归属、每日图片引用和回执均纳入验证与恢复；图片仍复用 OutfitImage/MediaAsset，删除衣服不删除历史引用。旧 `0.7.7-templates` 备份需使用旧应用恢复，不直接上传新版本强行恢复。发布前保留旧镜像、完整备份及数据摘要。

## 验证边界

Fake 工程回归与真实模型效果分别记录。三日、七日样例不等于所有天气、场合与衣橱都能达标；携带目标为软目标。Chromium 移动视口不代替 iOS Safari/手机真机；真实复验调用范围和实际结果见交付记录。

## 界面交互

详情先核对已保存行程摘要，再显式生成。每日方案与行李清单可页内定位，历史版本仅供查看。收拾进度以服务器确认值为准，可筛选待收拾项；提交失败保留原请求，未确认操作不会因刷新而自动重发。编辑草稿可保留返回，重置须明确确认；最近一次调整文字关闭后可在同一天继续，切换日期时重新填写；跨刷新以已提交原请求恢复为准。具体实现与验证见 [UI/UX 记录](history/2026-11-11-p7-8-ui.md)。
