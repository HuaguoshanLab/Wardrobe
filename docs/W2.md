## 配置与编辑

每季独立保存版本、城市/自定时段备注及有序需求行。需求行拥有稳定 UUID、名称、品类、子类 ID 集合、场合集合、标签 ID 集合、目标下限/上限、备注和启用状态。名称不参与匹配。目标两端必须同时填写或同时留空；0～0 有效。删除行作软删除，保留原 ID 和配置，不删衣服；关联的 W3 补充计划保留来源外键与原快照，并显示来源已停用。

整季显式保存使用 expected_version 和 Idempotency-Key；未创建季节只读返回 version=0。编辑、排序、停用、删除统一在季节草稿中完成，离开保护、失败原请求重发、版本冲突保留输入。复制其他季节只追加新 ID 的草稿行，保留目标季节已有行，保存才生效。

初始子类词表按品类提供可选名称，不自动给旧衣服归类。自定义子类可新增、改名、停用和重新启用；不删除稳定 ID，停用后保留已有关联及需求规则，但禁止新的关联。改名不改变匹配。修改前读取引用影响，再携带影响令牌保存；影响变化需重新核对。

## 统计口径

所有季节配置、子类、标签和完整单品在一个 PostgreSQL REPEATABLE READ 只读事务中读取，响应携带 stats_at、各季 config_versions。统计不从客户端当前分页累加。

仅未删除、非示例、持有单品计入真实库存。每行品类、当前季节、子类、场合、标签之间 AND，同字段 OR；不设限制的字段不判断。任何确定不匹配优先排除；缺少所需属性为待核对。匹配后状况为完好/轻微磨损，合身为合身/不适用，才计入确认有效 K。未知为 U；需要维修、严重损坏或不合身单独列为不计入有效数量。待洗、普通暂不可用、收纳、待处理决定不减少 K。

- matched_owned：明确符合分类规则的持有单品（状况可能待核对或不适用）。
- confirmed：K；pending：U，两集合互斥。
- available：K 中当前可穿数量；unavailable：明确匹配持有单品中暂不可用数量。
- needs_attention：分类未确定不符、但状况/合身已确定不符合的持有单品。
- planned：已关联此需求的尚未核销补充计划数量，单独展示，不计入 K/U；跨季共享计划不可逐行相加。
- 明细分已确认、待核对、不计入；不计入包含同品类但规则不符、需要处理、已退出和示例。已删除和导入草稿不展示为当前单品。
- 同一单品明确匹配多个启用需求行时显示跨季/用途覆盖。全衣橱总数按 garment_id 唯一计数；行数量/缺口不可简单相加。
- 标签被删除时保留需求规则 ID，行标记“规则待修复”，不默默放宽匹配、不输出缺口；用户移除或替换缺失标签后恢复计算。子类停用不破坏现有规则。

结论严格采用计划 K/U/L/H：无目标仅展示事实；K<L<=K+U 先核对；K+U<L 至少缺 L-K-U；L<=K<=H 已确认达标；K>H 超自定目标 K-H。缺口限定“已录衣橱”，先核对未录入、维修和共享替代，无自动购买/退出。

## 数量草稿

显式估算仅用于非正式用途的日常上装/下装/连衣裙轮换，不用于外套、鞋、配饰或正式着装。收集每周使用天数 0～7、洗衣间隔 1～60 天、晾干 0～30 天、单件重复穿次数 1～100、备用件数 0～100；上限、城市、季节时段和收纳备注由用户填写。

后端纯计算：ceil(每周天数 × (洗衣间隔 + 晾干天数) / 7 / 重复穿次数) + 备用件数。保留全部参数及解释；“采用估算”只写入编辑草稿，整季保存才持久化。无通用默认数量，不根据城市推断数量，不自动覆盖旧目标。估算参数单独校验，未采用的无效参数不阻塞合法手工目标；需求草稿仍经完整 schema 校验。

## 接口与持久化

- GET /inventory/{season}：季节配置、统计及共享覆盖；GET /inventory/configs：四季配置供复制。
- POST /inventory/{season}：整季版本化保存，返回已存配置。最多 100 行/季，目标 0～10000；数字严格整数，不接收布尔或小数。
- POST /inventory/estimate：只读估算，无数据库写入、无任务或模型调用。
- GET /garment-subtypes/suggestions：分品类可选词表；GET /garment-subtypes/{id}/impact；PATCH /garment-subtypes/{id}：版本与引用影响确认。
